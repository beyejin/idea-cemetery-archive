## 1. 문제 정의 (타겟부터)

**타겟**: 부트캠프·국비지원 과정 수강생. 우리 자신이 당사자라 페인포인트를 조사가 아니라 경험으로 정의할 수 있다.

**문제**: 기수가 끝나면 지식이 증발한다. 기술 질문과 해결 과정은 오픈카톡 스크롤에 묻히고, 기수가 수료하면 방과 함께 사라진다. 다음 기수는 같은 에러로 같은 삽질을 반복한다. 각자 노션·블로그에 정리하지만 링크가 산재하고 검증이 안 된다.

**왜 커뮤니티 구조인가** (튜터 기준): 웹 서버의 존재 이유는 "내 정보 + 다른 사람의 정보가 결합되어 산출물이 나오는 것". 이 서비스는 내 질문(+커리큘럼 맥락)과 선배 기수의 해결 기록이 결합되어 즉시 해결책이라는 산출물을 만든다.

## 2. 서비스 정의

- **질문·해결 스레드**: 기술 질문 → 답변 → 채택. 모든 글에 커리큘럼 맥락(기수·주차·과제)이 자동으로 붙는다
- **RAG 선제안 (핵심 차별 기능)**: 질문을 작성하는 중에, 과거 기수의 유사 해결 스레드를 벡터 검색으로 먼저 제시 — "이 에러, 2기수 전에 해결된 적 있습니다". 그 기록으로 해결되면 스레드끼리 연결되어 지식 그래프가 자란다
  - **안전장치**: 유사도 threshold 미달 시 선제안 UI를 아예 노출하지 않는다 (작은 코퍼스에서 엉뚱한 제안이 뜨는 것보다 안 뜨는 게 낫다)
- **권한 모델**: 재학생/수료생/멘토/운영진 역할 + 기수별 공개 범위 — 백엔드 권한 설계의 핵심 어필 지점
- **실시간**: 활동 피드(답변 채택·질문 전 해결), 내 질문에 답변 알림, 동시 접속 표시

> **v2로 연기**: 면접 후기 (수료 인증 계정의 검증된 익명 후기). 문제 가치는 인정하나 4주 범위에서 제외. 수료 인증 로직 자체는 권한 모델에 남겨 확장 지점만 유지한다.

**대표 지표: "질문 전 해결 비율"** — 질문이 등록되지 않고 과거 기록으로 해결된 비율. 오픈카톡이 구조적으로 만들 수 없는 숫자이며, 파일럿에서 실측해 발표한다.

**측정 이벤트 설계** (v2 신규):

1. 질문 작성 화면 진입 시 `draft_started` 이벤트
2. RAG 선제안 노출 시 `suggestion_shown` (선제안 스레드 ID 포함)
3. 선제안 클릭 후 **"이 기록으로 해결됐어요" 버튼** 클릭 → `resolved_by_suggestion` + 스레드 연결 생성
4. 질문 제출 → `question_posted`

`질문 전 해결 비율 = resolved_by_suggestion / (resolved_by_suggestion + question_posted)`. 보조 지표로 "선제안 노출 후 작성 이탈"(suggestion_shown 후 5분 내 무행동 이탈)도 집계해 버튼 미클릭 해결 추정치의 상·하한을 제시한다.

## 3. 차별점 — 경쟁 지형

| 기존 수단 | 정체 | 구조적으로 못 하는 것 |
|---|---|---|
| 오픈카톡·디스코드 | 현재의 실제 수단 | 휘발성 — 검색 불가, 기수 종료와 함께 소멸 |
| OKKY·인프런 커뮤니티 | 범용 개발 Q&A | 커리큘럼 맥락 부재 — "우리 학원 7주차 과제의 그 에러"를 모름 |
| 스택오버플로 | 글로벌 Q&A | 영어·높은 진입장벽·학원 무관 |
| 에브리타임 | 대학 커뮤니티 | 부트캠프는 대상이 아님 |
| 노션 공유 | 개인 정리 | 링크 산재, 권한 없음, 관리 주체 소멸 |

**차별점 선언**: "기수가 끝나면 증발하던 지식을, 학원의 집단 기억으로 만든다." 커리큘럼 맥락(과정·주차·과제)이 데이터 구조에 박혀 있어 범용 커뮤니티가 구조적으로 따라올 수 없고, 질문을 올리기 전에 과거 해결 스레드가 먼저 제시된다.

## 4. 튜터 기준 점검표

| 튜터 기준 | 이 기획의 대응 |
|---|---|
| 내 정보 + 타인 정보 → 산출물 | 내 질문+커리큘럼 맥락 + 선배의 해결 기록 → RAG 선제안이라는 산출물. 해결 시 스레드 연결로 지식 그래프 성장 |
| 체류 또는 실질적 베네핏 | 검색·Q&A로 반복 방문(체류) + "질문 전 해결"이라는 즉각 베네핏. 지표로 실측 |
| 정보가 공유되는 구조 | 교류가 늘수록 코퍼스가 커지고 검색이 정확해지는 자기강화 구조 |
| 권한·업로드 표준 설계 | 기수/역할별 권한, 수료 인증, 커리큘럼 스키마 표준 + 버저닝(기수별 커리큘럼 개정 대응) |
| 방향: 교육/정보/커뮤니티 | 교육 도메인의 정보 공유 커뮤니티 — 세 방향의 교집합 |
| RAG "세컨드 브레인" 예시 | 학원 단위의 세컨드 브레인 그 자체. 수업에서 배운 Spring AI 2.0 실습(rag-demo)을 실서비스로 확장 |

## 5. 아키텍처 — MSA 4서비스 + 이원 DB

| 서비스 | 담당 | 책임 | 저장소·기술 |
|---|---|---|---|
| 인증·권한 | A | 소셜 로그인(OAuth2), JWT, 역할(재학생/수료생/멘토/운영진), 기수 관리, 수료 인증 | MySQL, Spring Security |
| 게시 | B | 질문/답변/채택, 피드 조회(QueryDSL), 원본 저장 + 이벤트 발행(Outbox) | MySQL(원본), Kafka 프로듀서 |
| 검색·RAG | C | 인덱서 컨슈머(임베딩 생성), 하이브리드 검색(벡터+메타 필터), RAG 선제안·출처 표기 답변 | PostgreSQL+pgvector, Spring AI 2.0 |
| 알림·실시간·통계 | D | 알림 팬아웃(멱등), WebSocket 허브, 조회수·좋아요 카운터, 인기 랭킹, **지표 이벤트 수집** | Redis, Kafka 컨슈머, WebSocket(STOMP) |

*(v2 변경: 게시 서비스의 "면접 후기" 책임 제거, 통계 서비스에 지표 이벤트 수집 명시)*

**이원 DB 원칙 (핵심 설계 결정)**

- 원본(진실의 원천)은 MySQL 하나 — pgvector 쪽은 언제든 재구축 가능한 검색 전용 복제본
- 두 DB를 잇는 다리는 Kafka 이벤트뿐 — 이중 쓰기 금지. 글 생성·수정·삭제 → post 이벤트 → 인덱서가 임베딩 후 upsert/삭제 전파
- 결과적 일관성 — 방금 쓴 글은 몇 초 뒤 검색에 반영 ("검색 반영 중" 표시로 UX 흡수)
- 장애 대응 — 인덱서 실패 시 DLQ 격리 + 전체 재색인 배치, 원본-복제본 개수 대조 검증

검색·RAG 서비스는 학원 수업 실습본(rag-demo: Spring AI 2.0 + pgvector, 적재·검색·strict 템플릿·튜닝 실험 포함)을 시드 코드베이스로 포크하여, ① 수동 적재 → Kafka 트리거 ② TRUNCATE → 글 ID upsert·삭제 전파 ③ 단일 metadata → 커리큘럼 메타 + filterExpression ④ 동기 → 비동기 ⑤ 권한 결합의 5개 갭을 메우며 프로덕션화한다.

## 6. 커리큘럼 메타데이터 전략

| 메타데이터 | 획득 방법 | 사용자 부담 |
|---|---|---|
| 과정·주차 구조 | 운영자가 1회 입력 (과정명, 기수 시작일, 주차 제목 — 약 30분) | 없음 |
| 기수 | 가입 시 1회 선택 (프로필 저장) | 1클릭 |
| 현재 주차 | 자동 계산 (오늘 – 기수 시작일) | 없음 |
| 과제 | 해당 주차 과제 목록에서 기본 제안 | 0~1클릭 |
| 기술 태그 | 본문에서 자동 추출 (1차 키워드 사전, 2차 LLM) | 없음 |

검색은 벡터 유사도가 주력, 메타데이터는 필터·가중치로 보조 — "같은 에러라도 1주차와 9주차는 원인이 다르다"를 해결하는 하이브리드 구조.

**콜드스타트** (v2 강화): 팀원·동기의 기존 트러블슈팅 노트를 **목표 200건** 시딩 후 우리 기수 파일럿으로 축적. 시딩 진행률을 W1~W3 주간 체크 항목으로 관리하고, 200건 미달이어도 threshold 안전장치(2절) 덕분에 데모 품질은 방어된다.

## 7. 기술 스택 매핑과 실험 계획

| 기술 | 이 도메인에서의 필연성 |
|---|---|
| Kafka | 원본(MySQL)과 검색 프로젝션(pgvector)의 유일한 동기화 다리 + 알림·통계 팬아웃 |
| Redis | 조회수·좋아요 대용량 카운터(동시성 ①), 인기 랭킹(Sorted Set), RAG 결과 캐싱 |
| 동시성 제어 | 카운터 갱신 유실 방지, 답변 채택 경쟁 조건(채택 순간 삭제 충돌), 알림·인덱서 멱등성 |
| WebSocket | 실시간 활동 피드, 답변 달림 즉시 알림, 동시 접속 표시 |
| K6 | "과제 마감 전날 밤" 검색·질문 폭주 시나리오 — RAG 응답 지연·캐시 적중률·카운터 정합성 측정 |
| QueryDSL | 피드 동적 필터(기수·주차·상태·정렬) |
| OAuth2+JWT | 가입 마찰 최소화 + 역할 기반 권한 + MSA 무상태 인증 |
| EKS | 4서비스 + 스테이트풀 2종 운영, 마감 시즌 검색 서비스 스케일아웃 |

**동시성 실험 (발표 하이라이트)**: 조회수·좋아요 카운터를 ① 제어 없음(유실 재현) ② synchronized(다중 파드 무력화 증명) ③ DB 원자 UPDATE ④ Redis INCR + 주기 플러시로 교체하며 K6로 유실률·처리량 비교 → 최종 선택 근거 제시.

## 8. 4주 로드맵 (v2 재편)

| 주차 | 목표 | 완료 조건 |
|---|---|---|
| W1 | ERD+커리큘럼 스키마 확정, 4서비스 스켈레톤+CI, 소셜 로그인 관통, rag-demo 포크·서비스화, Compose(MySQL·PG·Kafka·Redis), **시딩 노트 수집 시작** | 가입 → JWT → 서비스 간 호출 E2E 1개 통과 |
| W2 | 게시 CRUD+피드, Kafka 파이프라인(글→인덱서→pgvector), 하이브리드 검색 API, **RAG 선제안 최소 버전(작성 화면에서 유사 스레드 표시 + threshold 숨김)** | 글 작성 → 수 초 내 검색 반영 브라우저 2대 시연 + **질문 작성 중 선제안 노출 E2E 통과** |
| W3 | **선제안 고도화**(채택-스레드 연결, "해결됐어요" 지표 이벤트, 출처 표기), 실시간 피드, 알림 팬아웃, 카운터·랭킹, K6 1차+동시성 실험 | 실험 데이터 표 완성, 선제안→해결 연결 E2E 통과 |
| W4 | EKS 배포+CD, 커리큘럼·시딩 200건 완료, 우리 기수 파일럿, K6 2차, 발표 준비 | 운영 URL에서 파일럿 1주 — "질문 전 해결 비율" 실측치 확보 |

*(v2 변경: RAG 선제안 최소 버전 W2로 이동, 면접 후기·수료 인증 제거로 W3 부하 해소, 시딩을 W1부터 주간 관리)*
